## 长期 AI 辅助开发常见问题与过程规范

## 一、长期 AI 开发容易出现的问题

- 样式/组件各处单独实现，缺少统一复用机制
- 硬编码较多，配置、路径、魔法值散落，灵活性和可维护性低
- 重复业务逻辑反复实现，缺少公共抽象
- 冗余代码、废弃实现残留，缺少清理机制
- 文档持续累积但缺少维护，容易过期、冲突、难以检索

这些问题可作为后续 code review、文档巡检和重构的检查项。

## 二、AI 开发前

- 技术调研与任务拆解
- 明确目标、边界和验收标准
- 识别高风险模块与需要人工介入的环节

## 三、AI 开发过程

### 1. 多模型协作

- 多模型协作，降低单一模型的局限性
- 核心疑难问题人工介入：
  - AI 负责定位核心问题、给出排查方向，人工判断和决策
  - 不熟悉的模块可让不同模型交叉讨论，人工再查阅验证
  - 改不好是常见情况，应及时止损，必要时废弃当前方案或采用替代方案

### 2. 并行开发

- 并行开发时使用 worktree 隔离工作区，合并时集中处理冲突

### 3. 测试

- 测试策略分层，按改动风险选择测试层级，避免简单修改就执行高耗时测试甚至全量测试
- 基础功能测试
- e2e 端到端测试
- 性能测试
- 安全测试
- CI/CD 自动化测试，做好环境隔离
- 移除机械的表面单元测试，保留基础可用性与复杂场景测试
- 定期复盘测试缺口并补测

### 4. Code Review

- 业务是否跑通
- 代码实现是否足够清晰、优雅、可维护
- 是否存在完全无用的测试
- 是否充分复用项目已有基建

### 5. 文档

- 定期巡检文档，按“AI 易检索、人类易维护”的目标重构，而不是简单删减
- 高频踩坑位置记录到 `AGENTS.md`

文档巡检可使用以下提示词：

```text
你是AI上下文工程师兼技术文档架构师。请把现有文档重构成“AI易检索、人类易维护”的结构，而不是简单删减。

【项目信息】
项目：
技术栈：
文档规模：约__份 / __MB
主要问题：
必须保留：
禁止改动：
根索引预算：≤3000 tokens
单份活跃文档预算：1K–5K tokens

【目标】
1. 每份活跃文档只承担一种意图：教程/操作指南/参考/解释。
2. 每类信息只保留一个唯一真相源，其他地方只引用不复制。
3. 活跃文档必须自包含、标题即分块、关键信息前置。
4. 默认归档：过期设计、历史计划、会话产物移入归档区，不进入AI上下文。
5. 根索引只放：安全红线、关键命令、架构约束、信息地图；不放详细知识。

【流程】
第一步：只审计，不改文档。
输出：
- 问题Top10
- 文档分类表：路径｜体积｜主意图｜动作（保留/拆分/合并/改为索引/归档/删除候选）｜目标路径｜理由
- 重复/冲突清单
- 唯一真相源映射表
- 目标目录树
- 根索引草案（≤3000 tokens）
- 分批执行计划（每批3–5份）
- 待确认项和风险

第二步：我确认后，再按批次修改。
每批输出：改了哪些文件、为什么、原文路径映射、回滚方法。

【硬约束】
不臆造缺失信息；不确定标“待确认”。
不删除事实内容，只标记归档/删除候选。
不改变技术含义。
先方案，后执行。
现在开始审计，不要直接改文档。
```

## 四、发版

- 用规范文档统一发版流程
- 发版时备份上一版，支持快速回滚与异常统计
- 保留兜底安全模式，作为最后保障
